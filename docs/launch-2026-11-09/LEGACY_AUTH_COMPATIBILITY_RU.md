# Совместимость старых паролей с Hostinger Admin

Новый backend раньше принимал только `scrypt32768`, поэтому сохранённые bcrypt-хеши Supabase нельзя было перенести с сохранением входа. Кандидат теперь проверяет существующие scrypt-записи и bcrypt cost 10 (`2a`, `2b`, `2y`). Это соответствует формату проверенного экспорта; [Supabase документирует хранение bcrypt в `auth.users.encrypted_password`](https://supabase.com/docs/guides/auth/password-security).

Используется закреплённый `bcryptjs` 3.0.3 без дополнительных зависимостей. Для существующих и неизвестных аккаунтов выполняются оба алгоритма с фиксированными параметрами; прежний лимит двух одновременных проверок и ограничения попыток сохранены. Это уменьшает различие вычислительных путей, но не является доказательством полного отсутствия временных побочных каналов. Неизвестный аккаунт не получает сессию даже при совпадении с dummy-паролем. Повреждённые записи и неподдерживаемая стоимость bcrypt закрывают доступ.

У bcrypt есть предел 72 UTF-8 байта. Код явно отвергает более длинный ввод, чтобы не принимать игнорируемый суффикс; scrypt продолжает проверять весь пароль в пределах действующего ограничения длины. Это поведение и независимые ASCII/Unicode/boundary-примеры проверены согласно [описанию bcrypt.js](https://github.com/dcodeIO/bcrypt.js#security-considerations). При наличии исторического пароля за пределом 72 байт потребуется отдельный управляемый владельцем путь смены; автоматическая смена не выполняется.

Проверка пароля не меняет хеш, роль, одобрение, блокировку или назначение workspace. Перед созданием сессии backend повторно блокирует строку профиля и проверяет актуальные флаги и хеш. Старые Supabase sessions/refresh tokens не принимаются новым backend. Импорт реальных аккаунтов и назначение workspace ещё не выполнены; этот код сам ничего не импортирует и не активирует Supabase.

## Проверки кандидата

- `pnpm test:passwords`: 7 тестов, включая независимые PHP PASSWORD_BCRYPT vectors, все три варианта префикса, неверный пароль, Unicode, границу длины и повреждённые записи.
- `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test:anonymous`: прошли локально.
- `pnpm audit --prod --audit-level=high`: известных уязвимостей в зависимостях нового backend не обнаружено на момент проверки.
- `node scripts/test-login-db.mjs --local-disposable`: 22 проверки реального HTTP-приложения с собственной MariaDB 13.0.2 без сетевого слушателя базы. Проверены bcrypt/scrypt-вход, сохранение ролей, запрет CRM для viewer, отказ pending/blocked, неверный пароль, неизвестный аккаунт, чужой Origin, неизменность учётных записей, сессия после перезапуска, блокировка действующей сессии и logout.

После теста оба процесса остановлены. Использованы только синтетические данные. Локальная MariaDB 13.0.2 **не** заменяет проверку Hostinger 11.8.9 и вход владельца после проверенного переноса аккаунтов. Эта проверка остаётся условием публикации.
