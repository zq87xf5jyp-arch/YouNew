# YouNew Phase 5 — план ограниченного запуска

Дата: 24 октября 2026 года. Статус: локально подготовлено, production deployment не разрешён и не выполнялся.

## Зафиксированный объём релиза

- Публичный пакет собирается только после `pnpm predeploy:check` и фиксируется скриптом `scripts/freeze-phase5-release.sh` с SHA-256 архива и отдельным реестром хэшей исходников.
- Production-каталог остаётся fail closed: 7 карточек доступны, 170 записей исключены. Десять заново подтверждённых станций находятся только в QA-релизе `amsterdam-v0.1.9`.
- Административная сборка фиксируется её Next.js `BUILD_ID`; host-specific admin package не создаётся до отдельного разрешённого шага.
- Рабочее дерево уже содержит изменения прежних фаз, поэтому фиксация выполняется воспроизводимым артефактом и реестром хэшей, без скрытого коммита и без изменения чужих файлов.

## Влияние 170 исключений

Проверка `DataProject/quality/phase5-stale-route-impact.json` доказала:

- 170/170 записей отсутствуют в текущем публичном JSON;
- 170/170 статических страниц отсутствуют;
- 170/170 URL отсутствуют в sitemap;
- пустых страниц и битых внутренних ссылок не создано;
- для исключённых карточек сохраняется настоящий HTTP 404, без массового редиректа на категорию и риска soft 404;
- десять подтверждённых кандидатов после принятия вернутся на прежние canonical URL.

## Последовательность запуска

### Gate 0 — отдельное разрешение владельца

В разрешении должны быть указаны SHA-256 публичного архива, окно работ и допустимый scope. До этого запрещены загрузка пакета, миграции, изменение DNS, production secrets и синтетические production-заявки.

### Gate 1 — live-only резервирование

1. Создать зашифрованный логический backup production PostgreSQL штатным `admin-dashboard/scripts/backup-postgres.sh`.
2. Сформировать metadata-only Storage inventory через `pnpm storage:inventory` и сохранить его хэш.
3. Отдельно скопировать payload bytes всех непустых Storage buckets; database dump содержит только Storage metadata.
4. Проверить backup через `restore-postgres.sh` в disposable PostgreSQL и записать доказательство восстановления.
5. Сверить количество бакетов, объектов и объём между inventory и копией payloads. Ни один production-файл не удалять и не перезаписывать.

Если любой пункт не подтверждён, запуск останавливается.

### Gate 2 — staging parity

1. Развернуть точный зафиксированный публичный архив в закрытом preview/staging.
2. Применить только уже проверенную disposable migration chain в изолированной staging-базе.
3. Проверить NL/EN главную, поиск, карточку, Add/Claim, privacy/terms, canonical, hreflang, sitemap, robots.txt, настоящий 404 и мобильный viewport.
4. Выполнить по одной явно маркированной EN и NL тестовой заявке через Edge endpoint, подтвердить сохранение и затем удалить только эти известные синтетические строки.
5. Проверить consent-gated аналитику: до согласия запросы не отправляются; payload не содержит query, email, названия бизнеса или свободного текста.

### Gate 3 — ограниченная production-публикация

1. Публиковать только хэшированный публичный архив. Не менять production database на этом шаге.
2. Сначала проверить `/`, `/nl/`, `/search/`, `/nl/zoeken/`, одну существующую карточку, `/business/add/`, `/nl/zakelijk/aanmelden/`, `/sitemap.xml`, `/robots.txt` и отсутствующий URL.
3. Сверить CSP, security headers, canonical/hreflang и отсутствие 170 исключённых URL в sitemap.
4. После проверки владельцем разрешить обычный трафик. Десять QA-кандидатов публикуются только отдельным принятием data release.

### Gate 4 — первые 24 часа

- Проверки доступности: сразу, через 15 минут, 1 час, 6 часов и 24 часа.
- Контроль: 5xx, CSP/JS ошибки, 404 по навигации, сохранённые заявки, consented analytics, Search Console sitemap status.
- Не считать отсутствие данных нулём: dashboard показывает «нет источника», пока Search Console или операционный реестр не подключены.

## Rollback

Триггеры: повторяющийся 5xx, невозможность сохранить заявку, утечка PII, неверный canonical/noindex, публикация исключённых карточек, нарушение consent gate.

1. Остановить расширение трафика.
2. Вернуть предыдущий хэшированный статический пакет.
3. Если миграций не было, базу не трогать. Если отдельная миграция была явно разрешена, применять её заранее задокументированный forward-fix или restore только после оценки потери данных.
4. Не выполнять массовое удаление заявок. Удалять можно только известные synthetic E2E records по их уникальному marker/receipt.
5. Зафиксировать время, симптом, пакет, решение и повторный smoke результат.

## Условия GO

- Полный локальный pre-deploy PASS.
- Exact release archive SHA-256 указан в разрешении.
- Production DB backup, Storage payload copy и disposable restore подтверждены в окне запуска.
- Секреты и production identifiers не попали в артефакт.
- 170 исключений сохранены либо принято отдельное изменение data release.
- Назначен человек, принимающий решение GO/ROLLBACK.

Без выполнения всех условий решение — **NO-GO**.
